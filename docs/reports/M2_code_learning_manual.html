让摄像头画面出现在浏览器里，代码到底做了什么？

你不需要先成为 C 语言专家。先抓住一条主线：摄像头不断产生 JPEG 图片，程序保存最新一张，再通过 HTTP 连续发给浏览器。

对象：第一次独立读项目代码重点：理解设计原因方法：流程优先，细节后置源码状态：M2 验证中
整份教程只围绕一个问题：“一帧图像从摄像头出发，经过哪些模块，最后怎样成为浏览器中的画面？”遇到看不懂的函数，先问它在这条路上负责哪一步。

00 / Before Code

读代码前，只补这几个必要概念

你现在不必系统学完整本 C 语言。下面这些概念足够支撑你读懂 M2 主线。

程序、进程、线程有什么区别？

程序 Program

磁盘上的可执行文件，例如 imx6ull-sense。它还没有运行。

进程 Process

程序运行后的实例。它拥有内存、文件描述符等资源。

线程 Thread

进程内部的一条执行路线。多个线程共享进程内存，但可以同时做不同工作。

在本项目中：只有一个 daemon 进程，但至少有主线程、摄像头采集线程，以及若干 HTTP 客户端线程。

怎样看懂一个 C 函数声明？

源码事实sense.h 中的公开函数
int config_load(const char *path,
                SenseConfig *config,
                char *error,
                size_t error_size);
返回类型int调用结束后给调用者一个整数结果
函数名config_load这组步骤的名字
输入path配置文件路径
输出地址config / error函数通过指针填充结果
声明结束;这里只说明接口，没有函数体

int 返回值在本项目中通常约定：0 表示成功，负数表示失败。但不是所有函数都完全相同，使用前仍应看调用处如何判断。

指针和结构体，不必先害怕

指针 Pointer

可以先把它理解为“内存地址”。SenseConfig *config 表示函数拿到配置对象所在位置，因此能直接填写调用者的配置。

结构体 Struct

类似一张有固定栏目表格。SenseConfig 把 width、height、fps_limit、http_port 等字段放在一起。

本项目最常见的 8 个词

帧 Frame视频中的一张静态图片。本项目一帧就是一段 JPEG 字节。
缓冲区 Buffer暂存数据的一块内存区域，可理解为周转托盘。
文件描述符 fdLinux 给已打开文件、设备或网络连接的整数编号。
设备节点 /dev/videoXLinux 把摄像头暴露成“像文件一样可打开”的入口。
互斥锁 Mutex共享资料柜唯一的一把钥匙，同一时刻只允许一个线程修改。
条件变量 Condition Variable通知铃：新帧到达时叫醒正在等待的 HTTP 线程。
MJPEG连续排列的 JPEG 图片。每一帧都能独立解码。
daemon长期在后台运行、持续提供服务的进程。
本节只需记住：摄像头线程负责生产帧，HTTP 线程负责消费帧，它们通过一块受锁保护的共享内存协作。
01 / Big Picture

先用一张图看懂整个项目

1. UVC 摄像头持续产生 MJPG 帧
→
2. capture_v4l2.c从内核取出一帧
→
3. state.c保存最新一帧
→
4. http_server.c包装成 MJPEG 流
→
5. 浏览器连续显示 JPEG

这条链路可以分成两半：

生产端

capture_v4l2.c 和摄像头打交道，不断生产新帧。

问题核心：怎样正确拿到下一张 JPEG？

消费端

http_server.c 和浏览器打交道，不断消费最新帧。

问题核心：怎样按浏览器认识的格式发送？

state.c 位于中间，负责让生产端和消费端安全交接。

谁在同时工作？

主线程
加载配置 → 创建采集线程 → 监听 8080 端口 → 最后组织退出
采集线程
找摄像头 → 配置 V4L2 → 反复取帧 → 发布最新帧
客户端线程
每连接一个浏览器就创建一个 → 发送首页、状态或视频流
为什么需要多个线程？等待摄像头、等待浏览器连接、向慢客户端发送数据都可能阻塞。如果全部放在一条执行路线里，任何一步卡住都会让其他工作停下。
本节只需记住：capture 生产，state 中转，http 消费，main 组织生命周期。

03 / Main Line A

第一条主线：程序怎样启动？

入口是 main()。它像流程负责人，只组织工作，不亲自实现摄像头采集或 HTTP 协议。

教学简化main.c 的真实顺序，省略错误输出
int main(...) {
    config_load(...);                   // 1. 读取配置
    install_signal_handlers();           // 2. 准备安全退出
    state_init(&state);                   // 3. 创建共享状态

    pthread_create(..., capture_thread_main, ...);
                                            // 4. 启动摄像头线程

    http_server_run(&state, config.http_port);
                                            // 5. 主线程监听浏览器

    state_request_stop(&state);          // 6. 通知所有线程停止
    pthread_join(capture_thread, NULL);  // 7. 等摄像头线程结束
    state_wait_for_clients(&state);      // 8. 等客户端线程结束
    state_destroy(&state);              // 9. 最后释放共享资源
}

为什么顺序不能乱？

  1. 必须先有配置，才知道如何工作。

    宽高、帧率和端口都来自 SenseConfig。

  2. 必须先初始化 AppState，再创建线程。

    线程启动后可能立刻访问锁和帧缓存；未初始化就是访问无效资源。

  3. 必须先通知停止，再等待线程。

    如果线程还在无限等待新帧，而主线程直接 join，程序可能永远等不到结束。

  4. 必须等全部线程结束，才能 destroy。

    否则其他线程可能继续访问已经释放的锁和内存。

sense.h 为什么存在？

不同 .c 文件需要共同认识 SenseConfig、AppState 和函数声明。头文件相当于模块之间签订的“合同”。

SenseConfig

程序想怎样运行：设备选择、宽高、帧率、端口等。

AppState

程序现在怎样运行：最新帧、帧数、客户端数、错误和停止标志。

StatusSnapshot

把某一时刻的状态复制出来，供 /status 生成 JSON。

CaptureContext

把配置和共享状态一起交给采集线程。

配置和状态不是一回事：“希望 640×480@30”是配置；“实际正在 /dev/video1 采集，当前 29.8 fps”是状态。

main.c 中三个小函数

handle_signal()：收到停止信号时做什么？
只把 g_signal_stop 设为 1。它故意不释放内存、不加锁，因为普通清理函数不一定能在信号处理器中安全调用。
install_signal_handlers()：安装哪些规则？
让 SIGINT 和 SIGTERM 调用 handle_signal；同时忽略 SIGPIPE，避免浏览器突然断开时整个进程被信号终止。
print_usage()：为什么也值得保留？
参数错误时明确告诉用户正确用法。它很小，但属于可诊断性设计。
本节只需记住：main() 负责顺序和清理。复杂算法放在模块中，入口保持短而清楚。
04 / Main Line B

第二条主线：一帧图像怎样到达浏览器？

内核填好 buffer摄像头产生一张 MJPG
→
VIDIOC_DQBUF采集线程取出可用 buffer
→
state_publish_frame复制为最新帧并敲铃
→
state_wait_frame客户端复制自己的帧
→
handle_stream包装并通过 socket 发送

为什么一帧要复制两次？

复制从哪里到哪里不复制会怎样
第一次V4L2 mmap buffer → AppState.framebuffer 归还驱动后，摄像头可能立即覆盖它
第二次AppState.frame → 客户端私有 bufferHTTP 发送较慢时，共享最新帧可能被下一帧覆盖

复制会消耗一些 CPU 和内存带宽，但它把生命周期变得清楚：驱动、共享状态、每个客户端各自拥有稳定的数据。

关键理解：这里没有保存“全部历史帧”。AppState.frame 像一块只展示最新通知的白板，新帧会覆盖旧帧。

frame_sequence 是什么？

它是最新帧的版本号。每发布一帧就加 1。客户端记住自己上次看到的序号，只有序号变大才发送新帧，因此不会无意义地重复发送同一张图片。

教学简化生产与消费关系
// 采集线程：生产者
copy_to_shared_frame(new_jpeg);
frame_sequence++;
wake_waiting_clients();

// HTTP 线程：消费者
while (frame_sequence <= my_last_sequence) {
    wait_for_new_frame();
}
copy_to_my_private_buffer();
my_last_sequence = frame_sequence;
本节只需记住：一帧的主路径是 capture_once → state_publish_frame → state_wait_frame → handle_stream。
05 / Main Line C

第三条主线：程序怎样安全退出？

安全退出不是直接“杀掉线程”，而是先发通知，让每个拥有资源的线程自己停下来并清理。

Ctrl+C / SIGTERM操作系统发出停止信号
→
handle_signalg_signal_stop = 1
→
各循环观察state_should_stop 返回真
→
线程自行清理STREAMOFF、munmap、close
→
main 最终销毁锁、条件变量、共享帧

为什么 handler 只改一个变量？

信号可能在任意时刻打断程序。加锁、打印、动态分配内存等普通操作此时可能不安全，因此 handle_signal() 只修改 volatile sig_atomic_t 类型的停止标志。

阻塞中的线程怎样醒来？

等待点如何避免永久卡住
HTTP 监听线程poll(..., 500) 最多等待约 500 ms，然后重新检查 stop
摄像头线程select(..., 2 秒) 有超时，并处理 EINTR
等待新帧的客户端pthread_cond_timedwait 最多约 1 秒；state_request_stop 也会广播唤醒
摄像头重试延时分成 10 次 200 ms，每次检查 stop
为什么不用一次很长的 sleep？假如睡 30 秒，用户发送 SIGTERM 后最坏要等近 30 秒。短等待加重复检查能兼顾低 CPU 与及时退出。
本节只需记住：停止标志负责“通知”，资源拥有者负责“清理”，main 负责“等待并最后销毁”。
06 / capture_v4l2.c

摄像头采集：把 V4L2 看成一套固定流程

V4L2 不是某一个函数，而是一组访问视频设备的规则。用户程序通过打开 /dev/videoX，再发送一系列 ioctl 命令控制摄像头。

ioctl 是什么？

普通 read 只能读数据；ioctl 用于向设备发送“查询能力、设置格式、申请缓冲区”等专用命令。

mmap 是什么？

把驱动管理的缓冲区映射到进程地址空间。程序能直接访问那块内存，减少额外数据搬运。

第一步：不要相信固定的 video 编号

同一个 UVC 摄像头可能暴露两个节点：一个是真正的 Video Capture，另一个只提供 Metadata Capture。重启或插拔后编号也可能变化。

教学简化select_camera() 的判断逻辑
for (video0 ... video63) {
    fd = open(candidate);
    capability = VIDIOC_QUERYCAP(fd);

    if (driver == "uvcvideo"
        && has_VIDEO_CAPTURE
        && has_STREAMING) {
        return fd;  // 这个节点才符合要求
    }
    close(fd);
}

device_capabilities() 还会区分设备整体能力与当前节点能力，防止把 metadata 节点误判为视频节点。

第二步：按顺序完成一次采集会话

  1. 选择并打开设备。

    select_camera() 返回正确节点的 fd。

  2. 请求 MJPG 格式。

    VIDIOC_S_FMT 设置 width、height、MJPEG，并检查驱动实际返回仍是 MJPG。

  3. 请求帧率。

    VIDIOC_S_PARM 使用 fps_limit。它失败时当前实现只打印 warning，因为有些设备仍可按自己的默认帧率工作。

  4. 申请和映射缓冲区。

    REQBUFS → QUERYBUF → mmap。当前代码最多管理 4 个 buffer，并要求驱动至少给出 2 个。

  5. 把空 buffer 交给驱动并启动。

    逐个 QBUF，然后 STREAMON。

  6. 循环取帧。

    select() 等待设备可读，DQBUF 取出已填充的 buffer。

  7. 复制并归还。

    检查 JPEG 以 ff d8 开头，调用 state_publish_frame()，然后 QBUF 把 buffer 还给驱动。

buffer 为什么要“取出再归还”？

QBUF空托盘交给驱动
→
摄像头填充驱动写入一帧
→
DQBUF程序取走满托盘
→
复制 JPEG保存到 AppState
→
再次 QBUF清空后继续循环

如果忘记再次 QBUF，驱动手里的空 buffer 会越来越少，最终采集停止。

最关键函数：capture_once()

它拥有一次采集会话的全部资源：camera fd、mmap 地址和 streaming 状态。成功或失败都从统一的 cleanup 路径执行：

教学简化统一清理思想
result = -1;
fd = open_camera();

if (某一步失败) goto cleanup;

// 配置、映射、取帧……
result = 0;

cleanup:
if (streaming) STREAMOFF();
munmap_all_buffers();
close(fd);
return result;

goto cleanup 在这里不是随意跳转，而是把多个失败出口汇聚到同一个释放顺序，减少遗漏。

为什么外面还有 capture_thread_main()？

capture_once() 负责“一次设备会话”；线程入口负责“会话失败后的策略”。失败时设置 degraded、等待约 2 秒，再重新枚举。这样摄像头后插入或短暂断开时 daemon 不必退出。

当前 M2 边界：只接受摄像头直接输出 MJPG，不实现 YUYV→JPEG 软件编码。因此 jpeg_quality 虽被读取，在当前采集链中并不会改变画质。
本节只需记住：找对节点 → 设置 MJPG → mmap 多个 buffer → DQBUF 取帧 → 复制 → QBUF 归还 → 出错统一清理并重试。
07 / state.c

线程共享状态：为什么需要锁和条件变量？

采集线程会写最新帧，多个 HTTP 线程会读最新帧。如果读写同时发生，客户端可能读到“一半旧、一半新”的数据，这叫数据竞争。

互斥锁：保证一次操作完整完成

教学简化state_publish_frame() 的关键临界区
pthread_mutex_lock(&state->lock);

// 锁住后，其他线程不能同时修改这组共享数据
resize_if_needed();
memcpy(state->frame, new_frame, frame_size);
state->frame_sequence++;
state->frame_count++;

pthread_cond_broadcast(&state->frame_ready);
pthread_mutex_unlock(&state->lock);

锁保护的不是某一行，而是必须保持一致的一组字段：frame 字节、frame_size、sequence、frame_count 和 fps。

条件变量：没有新帧时不要空转

错误做法是客户端不停检查 sequence，这会浪费 CPU。正确做法是：

  1. HTTP 线程发现没有新帧。

    它在 frame_ready 条件变量上睡眠。

  2. 采集线程发布新帧。

    更新数据后调用 pthread_cond_broadcast，相当于按响通知铃。

  3. HTTP 线程醒来重新检查。

    不能假设醒来一定有新帧，必须在 while 中再次判断条件。

为什么一定是 while，不是 if？条件变量允许“伪唤醒”，多个客户端也会一起醒来。醒来只表示“应该再检查一次”，不保证条件已经满足。

state_publish_frame() 和 state_wait_frame()

函数谁调用核心动作返回后谁拥有数据
state_publish_frame采集线程扩容共享内存、复制新 JPEG、加序号、通知客户端AppState 拥有共享副本
state_wait_frame流客户端线程等待新序号、扩容私有内存、复制 JPEG该客户端线程拥有私有副本

state_wait_frame() 使用约 1 秒的 timed wait。返回 0 表示暂时超时，可以继续等；返回 1 表示得到新帧；负数表示停止或错误。

状态模块还管理什么？

degraded

摄像头不可用时服务仍存活，/status 能告诉用户错误，而不是整个进程立即退出。

worker_count

所有 HTTP 线程数量。main 退出前必须等它归零。

client_count

当前正在看 /stream 的客户端数，用于状态展示。

StatusSnapshot

在锁内快速复制状态，解锁后再慢慢格式化 JSON 和发送网络数据。

本节只需记住：mutex 保证数据不会被同时读写破坏；condition variable 让客户端高效等待；sequence 判断“是不是新帧”。
08 / http_server.c

HTTP 与 MJPEG：浏览器为什么能把图片看成视频？

HTTP 服务端先创建一个socket，绑定 0.0.0.0:8080 并监听。每当浏览器连接，就为它创建一个客户端线程。

本项目只有三个地址

请求返回内容用途
GET /一小段 HTML，其中有 <img src="/stream">浏览器预览页
GET /stream无限延续的 multipart MJPEG实时画面
GET /statusJSON 状态观察设备、fps、帧数、客户端和错误

为什么 <img> 能显示动态画面？

普通图片响应只返回一个 JPEG。MJPEG 响应声明自己包含多个部分，每部分都是一张 JPEG。浏览器收到下一部分后更新 <img>，连续更新就形成视频效果。

协议事实/stream 响应的字节结构
HTTP/1.1 200 OK
Content-Type: multipart/x-mixed-replace; boundary=frame

--frame
Content-Type: image/jpeg
Content-Length: 18342

[JPEG 第 1 帧的 18342 个字节]
--frame
Content-Type: image/jpeg
Content-Length: 17690

[JPEG 第 2 帧的 17690 个字节]
...

boundary=frame 告诉浏览器用 --frame 分隔图片。每一部分的 Content-Length 必须精确等于该 JPEG 的字节数。

关键函数如何配合？

http_server_run()

创建监听 socket，poll 等待连接，accept 后创建 detached 客户端线程。

client_thread_main()

读取请求开头，解析 method 与 path，再分派到首页、状态或视频流。

handle_stream()

发送 multipart 顶层头，然后循环等待新帧、写分段头、写 JPEG、写换行。

send_all()

确保一段数据真的全部发送完成，而不是只调用一次 send。

为什么 send() 要循环？

TCP 只保证字节流可靠，不保证一次 send(fd, data, 20000) 就接受 20000 字节。它可能只接受一部分。send_all() 每次把游标向前移动，直到剩余长度为 0。

教学简化send_all() 的核心思想
while (remaining > 0) {
    sent = send(fd, cursor, remaining, MSG_NOSIGNAL);
    if (sent < 0 && errno == EINTR) continue;
    if (sent <= 0) return -1;

    cursor += sent;
    remaining -= sent;
}

/status 怎样生成？

handle_status() 先调用 state_snapshot()，在短暂持锁期间复制状态；解锁后再转义字符串、拼 JSON 和发送。

当前字段示意值会随运行变化
{
  "ok": true,
  "degraded": false,
  "device": "/dev/video1",
  "width": 640,
  "height": 480,
  "fps": 29.8,
  "frame_count": 1234,
  "client_count": 1,
  "motion_state": false,
  "event_count": 0,
  "last_error": null
}
M2 与 M3 的边界：motion_state 和 event_count 当前是固定占位值，不代表运动检测已经实现。
当前 HTTP 服务器为什么这么小？它只服务已知的三个 GET 路径，不支持完整 HTTP/1.1、keep-alive、认证或 TLS。这样更容易在 M2 建立闭环，但不应当作通用 Web 服务器。
本节只需记住：浏览器收到的不是“视频文件”，而是由 boundary 分隔的一张又一张 JPEG。

当前配置文件

字段通俗解释当前 M2 是否实际使用
deviceauto 表示动态寻找 UVC Capture 节点是
width / height请求画面尺寸 640×480是
fps_limit请求每秒 30 帧是，设备可能采用实际可支持值
http_port浏览器连接端口 8080是
jpeg_quality预留的软件 JPEG 质量否，当前直接转发摄像头 MJPG
event_log未来事件日志路径否，留给 M3
motion_*未来运动检测阈值和冷却时间否，留给 M3

config_load() 做了哪四层工作？

  1. 先填默认值。

    即使文件省略某个字段，程序也有基础值。

  2. 读取整个文件。

    打开、计算大小、分配内存、读取并加字符串结束符。

  3. 解析 JSON。

    识别字符串、整数、逗号、冒号和大括号，把已知键写入 SenseConfig。

  4. 验证语义范围。

    例如 width 必须在 1..4096，fps_limit 在 1..120，端口在 1..65535。

解析和验证为什么分开？"fps_limit": "fast" 是类型/语法错误；"fps_limit": 0 是数值范围错误。分层后错误更容易定位。

当前解析器是项目专用的扁平 JSON 解析器，不是完整通用 JSON 库。skip_space、consume、parse_string 等小函数只是把游标一步步向前移动。

Makefile 需要会到什么程度？

概念作用
SRCS → OBJS每个 .c 先编译为 .o，再把所有 .o 链接成可执行文件
-pthread启用并链接 POSIX 线程支持
-MMD -MP自动生成 .d 依赖文件，头文件变化时重新编译相关源码

构建命令主机验证与板端二进制是两种目标

编译成功不等于功能成功。编译只证明语法、类型和链接基本正确；板端摄像头、HTTP、浏览器与稳定性还要单独验证。
10 / Design Decisions

为什么这样设计，而不是看起来更简单的写法？

设计问题当前选择原因代价
摄像头节点动态检查 driver + Device Caps节点号会变化，还要排除 metadata、PXP、CSI 节点启动代码更长
采集格式直接要求 MJPG摄像头已压缩，ARM 不必实时做 JPEG 编码只支持 YUYV 的摄像头暂不可用
线程模型采集线程 + 每客户端线程采集、监听和慢客户端互不阻塞，逻辑容易理解客户端很多时线程数增长
帧保存只保留最新一帧实时预览重视低延迟，慢客户端直接跳帧不能回放，也不保证每帧送达
帧交接复制两次明确内核、共享状态、客户端各自的数据生命周期多消耗内存带宽
线程同步mutex + condition variable防止数据竞争，同时避免空转浪费 CPU必须严格遵守加锁规则
摄像头故障degraded + retry摄像头临时断开时状态接口仍可用，并能自动恢复需要维护错误和重试状态
HTTP最小自实现服务器MVP 依赖少，容易理解端到端链路不是完整、安全的通用服务器
退出合作式停止各线程清理自己拥有的资源，生命周期清楚所有等待点都必须定期观察 stop

一个重要的工程判断

“更少代码”不一定“更简单”。把摄像头采集、网络发送和共享内存全放进一个巨大循环，短期文件少，但任何阻塞和错误都会混在一起，后续更难测试、恢复和解释。

设计的目标不是炫技：当前拆分主要为了明确三件事：谁拥有资源、谁能修改共享数据、失败时由谁恢复或清理。
11 / Rebuild Without AI

从零复现：不要一次写完整项目

第一次独立实现时，最危险的做法是打开空文件就尝试写完 V4L2、线程和 HTTP。正确方法是建立一连串“能运行的小程序”，每一步都保留上一阶段能力。

你的规则：当前检查点没有通过，就不要进入下一步。这样错误只可能来自刚增加的少量代码。

检查点 1：写出能启动、能退出的最小程序

只实现：main() 打印一行文字并返回 0。

你在练习：源文件、编译、运行、exit code。

完成证据：主机执行后看到输出，echo $? 为 0。

练习骨架先自己写，不要复制完整项目
#include <stdio.h>

int main(void)
{
    printf("imx6ull-sense starting\n");
    return 0;
}

检查点 2：读取配置，但暂时不启动线程

只增加：SenseConfig、config_load()，成功后打印 width、height、port。

你在练习：结构体、指针输出参数、错误返回。

完成证据：正常 JSON 成功；把端口改成 0 时明确失败；文件不存在时明确失败。

这里先把 config.c 当成现成模块使用。等主线跑通后，再回头独立实现 JSON 游标解析器。

检查点 3：加入停止信号和 AppState

只增加：state_init、停止标志、SIGINT/SIGTERM、state_destroy。

你在练习：程序生命周期和资源逆序释放。

完成证据：程序循环等待，按 Ctrl+C 后在有限时间内返回 0。

检查点 4：只识别正确的摄像头节点

只增加：扫描 /dev/video0..63、打开、VIDIOC_QUERYCAP、检查 driver 与 Device Caps；暂不采集。

你在练习：fd、设备节点、ioctl、错误清理。

完成证据：能选中 UVC Video Capture 节点，并排除 metadata、PXP、CSI。

板端安全提醒：不要对 PXP 节点执行不明确的查询或采集实验。M1 已出现过 PXP 查询触发内核 Oops 的问题。动态选择时只接受符合 UVC Capture 条件的节点。

检查点 5：采集并保存一帧

只增加：MJPG 格式、REQBUFS、mmap、QBUF、STREAMON、一次 DQBUF、保存文件、QBUF、清理。

你在练习：V4L2 固定流程和 buffer 生命周期。

完成证据：exit 0、文件非空、头部 ff d8、尾部 ff d9、浏览器能打开。

这一步成功后再改成循环采集。否则“没有图”时你无法判断是配置、循环、线程还是网络的问题。

检查点 6：加入采集线程和最新帧共享

只增加：capture_thread_main、state_publish_frame、frame_count；暂不做 HTTP stream。

你在练习：线程参数、mutex、生产者。

完成证据：主线程每秒打印 frame_count，它持续增长；Ctrl+C 能完成 STREAMOFF、munmap、close 和 join。

检查点 7：先实现 /status

只增加：socket、bind、listen、accept、一个简单 GET 解析和状态 JSON。

你在练习：TCP 服务端、短 HTTP 响应、状态快照。

完成证据：curl http://192.168.7.2:8080/status 返回合法 JSON，frame_count 增长。

检查点 8：最后实现 /stream

只增加：state_wait_frame、multipart header、循环发送 JPEG。

你在练习：条件变量、客户端私有 buffer、长连接。

完成证据：响应类型正确；每段 boundary/Content-Length 正确；Windows 浏览器画面持续变化；刷新和重连后 daemon 仍存活。

检查点 9：加入故障恢复与稳定性

增加：degraded、摄像头重试、worker 计数、退出等待。

完成证据：摄像头拔出后 /status 报错但进程存活；插回后恢复；单客户端运行 30 分钟无明显 RSS 持续增长。

每一步都要问自己的四个问题

  • 这个新资源由谁创建？
  • 成功时谁使用它？
  • 失败时谁释放它？
  • 停止时怎样叫醒正在等待它的线程？
真正的独立复现，不是背下现有代码。你应该能从上述检查点重新推导出模块：配置、生命周期、采集、共享状态、HTTP、恢复。

13 / Glossary

术语表：以后看到这些词，不必再猜

API模块对外提供的调用方式；在 C 中常表现为头文件里的函数声明。
ABI编译后二进制层面的调用约定。本项目 MVP 暂不设计插件 ABI。
fd文件描述符。打开设备、文件、socket 后由 Linux 返回的整数句柄。
ioctl向设备发送专用控制命令的系统调用。
mmap / munmap把内核 buffer 映射进进程地址空间，以及取消映射。
V4L2Linux 视频设备用户态 API；规定查询、格式、buffer、streaming 流程。
UVCUSB Video Class。符合标准的 USB 摄像头通常由 uvcvideo 驱动。
MJPG / MJPEG由独立 JPEG 帧组成的视频格式；代码中的 fourcc 写作 MJPG。
SOI / EOIJPEG 开始/结束标记，常见字节分别为 ff d8 与 ff d9。
socket网络通信端点；服务端通过 bind/listen/accept 接收连接。
multipart一个 HTTP 响应内连续放多个数据部分，每部分由 boundary 分隔。
mutex互斥锁；保证同一时刻只有一个线程进入受保护区域。
condition variable条件变量；线程睡眠等待某条件变化，由其他线程 signal/broadcast 唤醒。
critical section临界区；访问共享数据时必须持锁的一段代码。
race condition竞态；结果取决于线程不可预测的先后顺序。
blocking阻塞；调用暂时不能继续，等待设备、网络或条件发生。
EINTR / EAGAIN系统调用被信号中断 / 当前暂时没有数据，通常需要按语义重试。
degraded降级状态；部分功能不可用，但进程和状态接口继续工作。
snapshot快照；在锁内复制某一时刻状态，之后使用副本避免长期持锁。
cross compilation交叉编译；在 x86 WSL 上生成能在 ARM i.MX6ULL 上运行的程序。

15 / Self Check

自测：先口述，再展开答案

1. 请用一句话描述一帧的完整路径。
查看答案
摄像头驱动填充 mmap buffer，采集线程 DQBUF 后复制到 AppState，HTTP 线程等待并复制自己的帧，再按 multipart JPEG 发送给浏览器。
2. 为什么不能永久写死 /dev/video1？
查看答案
节点号会随重启和插拔变化，同一 UVC 设备还可能有 Capture 与 Metadata 两个节点，必须依据 driver 和 Device Caps 判断。
3. 为什么状态里只保存最新一帧？
查看答案
实时预览重视低延迟。保存队列会增加内存和积压，慢客户端可以直接跳过旧帧。
4. mutex 和 condition variable 分别解决什么问题？
查看答案
mutex 防止共享数据被同时读写破坏；condition variable 让没有新帧的客户端睡眠并在新帧到达时被唤醒。
5. 为什么 DQBUF 后必须再次 QBUF？
查看答案
DQBUF 暂时把已填充 buffer 交给应用；QBUF 把它归还驱动继续填充。不归还会耗尽采集队列。
6. 为什么 send_all 不能只调用一次 send？
查看答案
一次 send 可能只接受部分数据；必须推进游标并发送剩余字节。
7. jpeg_quality 为什么当前不改变画质？
查看答案
当前链路直接转发摄像头输出的 MJPG，没有软件 JPEG encoder 使用这个参数。
8. 程序退出时，为什么最后才调用 state_destroy？
查看答案
采集和客户端线程仍可能访问 AppState。必须先通知、join/wait，确认使用者全部结束后再释放锁和内存。
9. 状态页正常但没有画面，第一步看什么？
查看答案
看 frame_count 是否持续增长。增长则优先检查 multipart/发送；不增长则优先检查 V4L2 与帧发布。
10. 如果让你重新实现，第一步会写 capture_once 吗？
查看答案
不会。先建立能启动退出、读配置和管理状态的小闭环，再做节点识别和单帧采集，最后才组合完整循环与 HTTP。
达到“会写”的判断标准：不看源码也能画出启动、单帧和退出三条流程，并能按检查点 1～8 说明每一步新增什么、如何验证、失败时查哪个模块。
