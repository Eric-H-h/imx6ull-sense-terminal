1. 我当前正在执行什么

当前结论：M2 第一版代码已经写入、主机编译通过、ARM 交叉编译通过，并已部署到 i.MX6ULL 板端。daemon 已自动选中 /dev/video1，持续采集 MJPG 640×480，HTTP /status 可从 WSL 访问。

当前边界：代码处于未提交工作区，仍是 M2 初版；不能把“板端状态接口成功”直接等同于“M2 全部完成”。浏览器画面、multipart 完整性、CPU/稳定性和文档证据还需要闭环。

3. 代码设计框架与运行数据流

USB UVC 摄像头设备原生输出 MJPG
本次图像节点 /dev/video1
capture_v4l2QUERYCAP · S_FMT
MMAP · DQBUF/QBUF
AppState 最新帧mutex + condition
只保存最新 JPEG
http_server/ · /status · /stream
每连接一个 worker
浏览器multipart/x-mixed-replace
<img src="/stream">

线程模型

主线程
解析 -c、加载 JSON、安装信号处理、启动 capture thread，然后在 http_server_run 中监听 8080。收到 SIGINT/SIGTERM 后通知所有线程退出。
Capture 线程
动态扫描 UVC Video Capture 节点，初始化 V4L2 mmap，持续取出 MJPG 帧并覆盖 AppState 中的最新帧；失败时设置 degraded 并每 2 秒重试。
HTTP worker
每个 TCP 请求使用一个短生命周期线程。普通页面和状态请求立即返回；stream worker 等待 frame_sequence 变化并发送最新 JPEG。

关键设计决策

  • MJPG pass-through：摄像头已经输出 JPEG，本阶段不引入 libjpeg，也不做 YUYV 编码，降低 Cortex-A7 CPU 压力。
  • 动态节点识别：不依赖 /dev/video1 的偶然编号，实际选择条件是驱动名和 Device Caps。
  • 最新帧模型：不建立历史帧队列。HTTP 客户端慢时跳过旧帧，而不是推高内存占用和延迟。
  • degraded 不退出：摄像头缺失时 HTTP 仍可返回可解释状态，为后续 M4 systemd/故障注入保留正确语义。
  • 范围控制：M2 不做 motion、录像、认证、OV5640、systemd 和复杂网页。

7. 当前风险、缺口与不确定项

尚不能宣称 M2 完成。最关键的用户可见验收“浏览器看到持续画面”还没有被确认，multipart 样本也未完成字节级检查。
风险/缺口影响当前缓解状态
浏览器未确认HTTP 状态成功不代表浏览器解码和刷新成功直接访问板端首页并观察动态画面最高优先级
multipart 字节检查中断尚未保存 boundary 与 JPEG SOI/EOI 的正式证据复用已采样的 WSL /tmp 文件，不必重新采集待检查
仅支持原生 MJPG不支持只输出 YUYV 的摄像头当前摄像头已验证 MJPG；YUYV 编码不进入 M2 第一版已知限制
PXP 历史 Oops错误查询 /dev/video0 可能触发 BSP bug代码只用 QUERYCAP 识别能力，不执行 --all；真正采集只选 uvcvideo已绕过
无认证同一网络内任何客户端均可访问MVP 仅用于受控 LAN 演示，文档明确限制范围外
构建 .d 文件未忽略Git 状态出现未跟踪依赖文件提交前更新 .gitignore 或 clean 后确认待清理
