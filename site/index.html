工程目标

实时性

保持约 30 FPS 的 MJPEG 推流；慢客户端可以跳帧，但不能堵住采集。

单客户端 30 分钟全程约 30.0 FPS，采集与发送解耦。

资源意识

在 i.MX6ULL 上控制 CPU 与内存；运动检测用低频灰度抽样，不拆主链路。

3 FPS × 160×120 灰度；全栈 RSS 2968 KB（delta 0），CPU 约 16.3%–16.6%。

可恢复性

摄像头、日志、进程故障都有可诊断状态；无人值守也能跑。

缺失摄像头保持 degraded；崩溃由 systemd 拉起；配错退出码 78 不风暴。

系统架构

UVC 采集写入唯一的 latest JPEG；HTTP 与 motion 都是这格的消费者。systemd 包着进程生命周期，不是数据通路上的一环。

默认：摄像头 → 采集 → 唯一 JPEG 槽。浏览器走 HTTP 推流；motion 以约 3 FPS 抽样同一槽。选中模块可看职责与源码位置。

工程决策

latest-frame 与慢客户端

问题 浏览器读取可能慢于采集。

约束 不能无限排队，也不能让 HTTP 堵住 capture。

决策 AppState 只保留最新完整 JPEG 和递增 sequence。

取舍 慢客户端会跳帧，但不堆积延迟。

结果 采集与发送解耦；单客户端约 30 FPS。

证据 · M2 推流 · state.c

低频运动检测

问题 每帧全分辨率 JPEG 解码会打满 ARM CPU。

约束 不能明显拉低 MJPEG 主链路帧率。

决策 约 3 FPS 抽样，libjpeg 1/4 缩到 160×120 灰度再帧差。

取舍 不追求逐帧定位，换稳定开销。

结果 推流保持约 30 FPS；静止 0 误报，挥手 10/10。

证据 · M3 motion

摄像头缺失不退出

问题 USB 摄像头可能断开，节点号也会变。

约束 硬件短暂不可用不应让整个服务退出。

决策 按 uvcvideo + Video Capture + Streaming 重新枚举，进入 degraded 并重试；跳过 PXP 等非 Capture 节点（查询曾触发 Oops）。

取舍 状态模型更复杂，恢复不靠 systemd 重启。

结果 同一进程完成热插恢复。运行中拔出见 ADR-0004 与 M3；M4 D2-B 是启动时无摄像头再插入。

ADR-0004 · M3 · PXP Oops

systemd 故障契约

问题 所有退出都自动重启，配错会造成风暴。

约束 崩溃应恢复；正常关闭和永久配置错误不应循环。

决策 SIGTERM 退出码 0；配置错误专用退出码 78，unit 使用 Restart=on-failure 与 RestartPreventExitStatus=78。

取舍 必须把退出语义写进 unit，不能只靠重启。

结果 kill -9 约 3 秒拉起新 PID；http_port=0 保持 failed，12 秒无风暴。

证据 · M4 故障注入 · imx6ull-sense.service
